# Архітектура Build Engineer AI Agent

## Призначення

Проєкт містить невелику Rust-програму Hello World, але його основна мета —
показати повторюваний процес автоматизації збірки. Build Engineer AI Agent
перетворює запит розробника на послідовність перевірюваних етапів і не
дозволяє завершити роботу без базової Cargo-структури, тесту та
кросплатформного CI.

Агент вирішує такі проблеми:

- відсутність єдиної очікуваної структури Rust-проєкту;
- ручне та непослідовне виконання `cargo check`, `cargo build` і `cargo test`;
- пропущені юніт-тести під час локальної розробки;
- розбіжності між локальною перевіркою і GitHub Actions;
- відсутність перевірки на різних операційних системах;
- нечітка діагностика помилок під час підготовки збірки.

## Компоненти

### Agent manifest

`.github/agents/build-engineer.agent.md` — декларація ролі, області
відповідальності, дозволів, обмежень, доступних skills і критеріїв
завершення. Frontmatter робить агента доступним у picker VS Code, а тіло
визначає операційні правила.

### Skills

Агент очікує три спеціалізовані skills:

- `project-scaffold` відповідає за Cargo-маніфест, `src/main.rs` і базову
  структуру;
- `build-and-test` виконує форматування, перевірку, збірку та юніт-тести;
- `github-actions` готує workflow і перевіряє матрицю операційних систем.

Skills є спеціалізованими етапами, а не незалежними агентами: вони
отримують контекст від оркестратора та повертають структурований результат.

### Commands

Локальні `ci.sh` і `ci.bat` є явними командами відтворення build-and-test
етапу. Вони виконують release-збірку та тести. Окремі Cargo-команди
залишаються доступними для діагностики конкретного збою.

### Orchestrator

Оркестратор керує переходами між етапами та не запускає наступний етап до
отримання успішного результату попереднього. Типова послідовність:

```text
Inspect -> Scaffold -> Build and test -> CI setup -> Verify
```

Він також контролює межі безпеки: зміни обмежені репозиторієм, видалення
заборонене без дозволу, а секрети та операції переписування Git-історії не
допускаються.

## Передавання даних між етапами

Кожен етап формує звіт із такими даними:

1. `stage` — назва етапу;
2. `status` — `success` або `failed`;
3. `changed_files` — перелік змінених проєктних файлів;
4. `commands` — виконані команди;
5. `diagnostics` — попередження та помилки;
6. `artifacts` — створені Cargo- або CI-файли.

Оркестратор передає цей звіт наступному етапу як контекст. Наприклад,
`build-and-test` використовує список файлів, створений `project-scaffold`,
а `github-actions` перевіряє, що команда тестування та назви платформ
відповідають результату локальної перевірки.

## Обробка помилок

Помилка є явною: етап повертає `failed`, команду, код завершення та
діагностику. Оркестратор:

1. зупиняє нормальний перехід до наступного етапу;
2. передає точну причину на етап виправлення;
3. повторно запускає невдалу перевірку після зміни;
4. завершує workflow лише після успіху або формує фінальний звіт про
   невиправлену помилку.

Заборонено маскувати збій порожнім результатом або мовчазним fallback.
Якщо Rust/Cargo відсутній, це повідомляється як інфраструктурна помилка, а
не як успішне проходження тестів.

## CI/CD

`.github/workflows/ci.yml` використовує матрицю `ubuntu-latest`,
`windows-latest` і `macos-latest`. Для кожної платформи workflow встановлює
stable Rust toolchain і запускає відповідний локальний скрипт. Після
успішного скрипта крок `actions/upload-artifact@v4` зберігає
файл `target/release/hello` (`hello.exe` на Windows) під ім'ям
`hello-${{ matrix.os }}`: `hello-ubuntu-latest`, `hello-windows-latest` або
`hello-macos-latest`. Параметр `if-no-files-found: error` не дозволяє
успішному запуску створити порожній artifact. У результатах workflow
доступний release-виконуваний файл відповідної платформи.
